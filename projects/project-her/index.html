The problem: coordinating a complete video workflow

A short video requires more than a model response: a usable script, relevant visuals, narration, captions, scene transitions, and a playable export. Article quality and available media vary, so each handoff affects the final result.

HER is my personal build, separate from employer-owned engineering work and hackathon prototypes. I connected AI content processing with media preparation, programmatic composition, an input experience, and a deployed application.

From input to MP4

The hosted interface accepts a topic, story, or article URL and exposes narration, duration, visual style, renderer, and Classic/News options. Its intended workflow is:

  1. 01 · Input & optionsBrowser form collects content and creator settings.
  2. 02 · Content planningBackend content processing and Gemini scripting prepare narration and scene descriptions.
  3. 03 · Narration & captionsSpeech audio and word timings provide a shared basis for the subtitle timeline.
  4. 04 · Visual assetsRetrieved or generated media is selected for the planned scenes.
  5. 05 · CompositionRemotion uses React compositions to combine visuals, audio, captions, and transitions; FFmpeg supports media processing.
  6. 06 · Preview & downloadThe app presents progress and, on a successful job, a video artifact for playback and download.

The repository now supports source-level inspection of the pipeline. The sample demonstrates a completed local Remotion render using saved HER narration and assets. A new, complete hosted generation run has not been tested.

Architecture and engineering decisions

Separate creator and renderer. The deployed input interface uses HTML, Bootstrap, and JavaScript. The backend uses Python/Flask, served by Gunicorn; React belongs to Remotion composition. The portfolio links directly to the standalone app, keeping its rendering lifecycle and paid services independent of portfolio hosting.

Model output becomes a rendering plan. Gemini content processing sits upstream of narration and scene composition. The engineering boundary is the handoff between generated text, timed audio, visual assets, and a deterministic video timeline. The editorial path uses validated Pydantic timelines, explicit word/section timing, asset provenance, staged media, and React compositions. Source research and supplied-account processing remain distinct in News mode. Schema validation makes handoffs inspectable; it does not guarantee factual accuracy or a good visual match.

Track long-running work outside the page request. The Flask server starts worker threads, tracks jobs in memory, and streams stage events over SSE. The client falls back to /api/result polling when streaming drops. News cancellation uses a threading event checked by the pipeline. This keeps the page request separate from rendering, but jobs and results are not durable across instance restarts. Docker runs one Gunicorn worker with eight threads and a 900-second timeout; those image settings are not a measurement of the deployed Cloud Run resources.

Package media dependencies together. I containerized and deployed the project on Google Cloud Run with the Python and media-rendering dependencies. Rendering competes for CPU and memory, and request limits and cold starts affect the experience. No verified resource configuration, throughput, or render-time benchmark is published here.

What I implemented

I built and deployed the personal video-generation workflow: connecting the input experience, model-based content planning, narration, visual assets, subtitle timing, and Remotion rendering, then packaging the application for Cloud Run.

Concrete source boundaries are web_ui.py and templates/index.html for the creator/job API; agent/orchestrator.py for the general flow; agent/news_pipeline.py for News routing; agent/editorial/pipeline.py, audio.py, director.py, planner.py and render.py for narration-driven timelines and delivery; and remotion/src/editorial/EditorialVideo.tsx for frame composition. The Dockerfile packages Python, Node, FFmpeg, fonts and browser dependencies. These modules were inspected; their presence is distinct from a new hosted end-to-end execution test.

Constraints and tradeoffs

Visual relevance and media rights. A relevant search term can still produce an unrelated image. Retrieved media needs rights and provenance review before publication. Generated imagery is illustrative and should not be presented as documentary evidence, especially in News mode.

Caption synchronization. Word timings, audio duration, and scene boundaries must agree. Speech pacing and failed alignment can produce clipped captions or drift; the saved sample carries Whisper forced-alignment word timestamps and low-confidence warnings. Its captions are derived from those saved marks; no general alignment-accuracy benchmark is claimed.

Latency and third-party failures. Model, narration, and media providers can time out or return unusable assets. Longer inputs increase work and potential cost; CPU, memory, and cold starts constrain rendering. The server has per-process daily/visitor caps and a concurrent-job limit. These counters reset on restart and do not form a distributed quota; preview/provider exposure and proxy IP trust still need a security review. Result retention is in memory. No production reliability guarantee follows from these controls.

Input quality and factual risk. Ambiguous prompts, inaccessible URLs, and weak source material affect the script. News controls expose research/editorial choices, but they do not guarantee factual correctness. Source review and a distinction between factual and illustrative assets remain necessary.

Next mitigations to validate. Durable jobs/results and shared quotas, robust client-IP trust, input-length and spend budgets, guarded preview usage, and provider-specific retry/deadline review are follow-up work. Existing manifest validation and local render checks are implemented separately; these recommendations are not claims of completed safeguards.

Validation, evidence, and current status

On 13 October 2026, the public application landing page returned HTTP 200. Its HTML and client logic were inspected, and its idle interface was captured separately as the application-preview fallback. No generation was submitted and no paid API credits were spent during this portfolio update.

The owner supplied and approved output/reference_parity_v2/editorial-remotion.mp4. ffprobe reports 56.128 seconds, 1080×1920 at 30 fps, H.264 video and AAC audio; a full FFmpeg decode completed without errors. The published file is byte-identical to that artifact. Those are file measurements, not generation speed or quality benchmarks. The original supplied account and rendered narration were recovered from the saved preview and manifest.

The local reference-v2 review script reuses saved narration, word marks, and illustrative assets without new provider calls. The sample has known limitations: a generic opening hook, uneven historical artwork, static holds, and low-confidence alignment marks. It demonstrates this rendering configuration, not every input or live cloud availability. No completion-rate, cost, throughput, or commercial-adoption benchmark is claimed.
